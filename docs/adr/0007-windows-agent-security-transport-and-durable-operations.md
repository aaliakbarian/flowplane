# ADR 0007: Secure the Windows Agent and Preserve Durable Native Operation Evidence

- **Status:** Accepted
- **Supersedes:** None
- **Superseded by:** None

## Context

Milestone B needs a small installable/uninstallable Windows Service, downloadable from the operator UI, for the first durable manual SSIS execution. The controlled SQL-authenticated B-02 create call returned 27123/state 1; no execution ID was returned and configure/start were not reached. Preserve that evidence: the approved Windows route is an explicit follow-on, not a successful SQL-authentication proof or a silent fallback.

The operator conditionally authorized acceptance after exact-document and independent architecture review. That review found no unresolved architectural issue; this record is prepared as **Accepted** for the final documentation staging gate. It does not change Accepted [ADR-0001](0001-control-plane-execution-plane-separation.md), [ADR-0004](0004-capability-based-data-pipeline-provider-architecture.md), [ADR-0005](0005-execution-lifecycle-authority-and-reconciliation.md) or [ADR-0006](0006-built-in-secret-storage-and-external-root-key.md). Acceptance records architecture, not implementation or external-operation authorization. The [Milestone B plan](../development/milestones/milestone-b-first-durable-manual-ssis-execution.md) retains registration, revision, parameter-free profile, external observation and task boundaries.

Execution and AgentHealth are mandatory operational capabilities. HostObservations and DataFlowTelemetry require bounded feasibility reports, not production monitoring implementation. No universal Host/metrics model, arbitrary remote management, broker, new worker service, historical SSIS versions or debugger-parity claim is introduced.

## Decision

The decision is outbound bounded HTTPS polling, exact-pinned per-agent mTLS, a dedicated Windows service identity, PostgreSQL-authoritative execution and a minimal local operation journal. These contracts form one security boundary; no code, migration, service installation, permission setup or native operation is authorized by recording them.

### 1. Separate identities and least privilege

| Identity | Authority |
| --- | --- |
| Human OIDC issuer + subject | Existing deny-by-default operator/resource policy; no native impersonation. |
| Agent UUID + exact public client certificate | Authenticate an installation; only assigned resources and typed operations. |
| Windows service token | Access its private key/journal and authenticate to SQL using Integrated Authentication. |
| SQL/SSISDB principal and permissions | Actual catalog visibility and native execution rights; enrollment does not grant them. |

Initial candidate: co-located standalone SQL Server and virtual account `NT SERVICE\FlowPlaneAgent`. Do not use LocalSystem, local Administrators membership, the installing administrator or an interactive user's token. Elevation for installation is separate from runtime authority. Service binaries and configuration are not writable by the service; its key/journal directories have narrowly scoped ACLs. A local setup helper uses authenticated, ACL-restricted local IPC to the service and never exports its private key.

The installer creates the service under that account, enables/verifies its service SID and records the resolved SID for key/file ACLs. Only local Administrators/System and the explicitly authorized elevated setup session may use setup IPC; validate the calling Windows token, never a caller-provided user name. Do not permit arbitrary local users to pair/rebind the service. An administrator separately reviews the following **future setup specification**, not commands to execute during planning:

1. Register the service with SCM (`obj= NT SERVICE\FlowPlaneAgent`, no managed password); configure a service SID using `sc.exe sidtype FlowPlaneAgent unrestricted` and verify with `sc.exe showsid`/`qc`. The installer must quote the executable path and reject pre-existing mismatched service configuration rather than overwrite it.
2. Under approved Windows SQL administration, create or verify the exact Windows login `[NT SERVICE\FlowPlaneAgent]` and its SSISDB user. Match the SID; do not repurpose a same-name/different-SID principal. Installation/enrollment never executes SQL grants.
3. Resolve `catalog.folders.folder_id` and `catalog.projects.project_id` for only the approved folder/project. Through public `catalog.grant_permission`, proposed grants are folder READ (`object_type=1`, `permission_type=1`), project READ (`2`, `1`) and project EXECUTE (`2`, `3`) to that user's principal ID. No folder-wide READ_OBJECTS/EXECUTE_OBJECTS, CREATE_OBJECTS, MODIFY_OBJECTS, permission management, db_owner, ssis_admin or sysadmin. The exact targets and grants require separate approval.
4. Prove actual READ/MODIFY on its created execution/operation for configuration/start, plus the required project READ/EXECUTE. Do not assume ownership or project grants automatically prove this. If necessary, separately review narrowly scoped operation READ/MODIFY (`object_type=4`, permission 1/2) by an authorized administrator; never implement a self-grant/elevation path. No environment READ is required for the null-reference fixture.
5. Inspect `sc.exe qsidtype`, the running process token's user/service SID and enabled groups, effective private-key/journal access, and denied writes to binaries/configuration. `showsid`/`qc` alone do not prove the running token. Record SQL's actual login/authentication identity on the service's connection. Independently prove create, each approved configuration call, start and exact-ID observation under that token. Interactive success, heartbeat and effective permission rows are insufficient. Stop on failure; no authentication fallback.

These are documented least-privilege candidates, not runtime feasibility evidence. B-02 has two separately recorded proof tracks: **A**, interactive Windows Integrated Authentication feasibility under the explicitly approved interactive identity, can proceed independently of Agent Foundation #28 after B-01 and external-operation approval; **B**, actual Windows Service-token execution proof, requires foundation readiness and the separately approved service identity/grants. Record both actual tokens, SQL identities, permissions and per-operation results. Interactive success neither completes B-02 nor unlocks execution-specific implementation; actual service-token proof remains mandatory. No execution support claim until both required B-02 proof tracks pass. SSIS package runtime identity is not necessarily its caller's Windows identity. Domain/gMSA and remote SQL are separate deployment profiles; a virtual account uses the computer identity for domain network access, not its local service SID. Do not introduce account-password mirroring or a double-hop workaround.

Existing A-09 SQL discovery/read credentials stay encrypted in Core. The execution binding explicitly captures AgentId, service/source identity and versions; no SQL password is sent to the agent. A source-qualified native execution ID cannot be rebound to another server after a provider/agent change.

### 2. HTTPS listener and exact client trust

Use short outbound polls, one bounded offer per response, not a persistent channel. Initial defaults proposed for implementation review: idle poll 5 seconds with jitter; heartbeat 15 seconds; stale contact 60 seconds; bounded RPC timeout 10 seconds; maximum command document 64 KiB. Native execution duration is independent of these HTTP deadlines. Read-only retries use bounded backoff; mutation ambiguity never triggers a retry.

Add a dedicated agent-facing HTTPS listener in the **existing ASP.NET Core backend**, proposed port 8443. The existing browser-facing Nginx/API listener cannot serve agent routes. Select the trust boundary using the actual local listener/TLS connection, not Host, X-Forwarded-Port or other caller headers. Agent credentials cannot authorize human JWT endpoints. Browser Nginx does not forward client certificates; do not register certificate-forwarding middleware or infer identity from any certificate header.

The following is the exact .NET 10 API configuration contract, not application code added by this ADR:

| Layer | Required setting/behavior |
| --- | --- |
| Kestrel endpoint | Endpoint-specific `Listen`/`UseHttps` with a separate server-auth certificate; TLS 1.2/1.3; no agent HTTP endpoint or credential-bearing redirect. |
| Client handshake | `HttpsConnectionAdapterOptions.ClientCertificateMode = ClientCertificateMode.AllowCertificate`. No certificate is permitted only for the narrowly scoped pairing claim. All operational routes require mTLS; no per-path TLS renegotiation. |
| Self-signed handshake validation | Set `ClientCertificateValidation` explicitly. It accepts only an exact DER pin in the committed pending-proof, active or bounded RetiringReceiptsOnly credential registry and a valid strict client profile. Unknown presented certificates fail. Never use `AllowAnyClientCertificate()` or an unconditional true callback. The ordinary platform-chain callback alone rejects these private self-signed leaves. |
| Pin lookup at handshake | Use an immutable in-process snapshot of committed exact public pins (pending-proof, active, bounded receipt-only retiring), not a blocking database call in the synchronous callback. Load before enabling agent readiness and update after enrollment/rotation commits. Snapshot failure fails closed. Pending pins authorize only proof/status recovery; retiring pins only the receipt recovery below. Neither grants operational authority. Stale snapshot entries cannot grant operation authorization. |
| ASP.NET authentication | A separate explicit certificate scheme with `AllowedCertificateTypes = CertificateTypes.SelfSigned`, `ValidateCertificateUse = true`, `ValidateValidityPeriod = true`. Do not replace the existing JWT default. `OnCertificateValidated` resolves the exact registered credential and replaces subject-derived authority with the database AgentId. |
| Strict profile | Verify a genuine self-signature, non-CA leaf, RSA-3072/SHA-256 initial profile, digital-signature usage and an explicit clientAuth EKU (`1.3.6.1.5.5.7.3.2`). Reject absent/other-only EKU, malformed/unsupported extensions/keys and invalid lifetime. Built-in usage validation alone also accepts no EKU, so it is insufficient. |
| Pin identity | SHA-256 of exact certificate DER plus exact DER equality on a digest conflict. SPKI is additional key evidence, never authority to substitute a different certificate. Subject, issuer text and SHA-1 thumbprint are not authorization keys. |
| Revocation | For these self-signed leaves, chain CRL/OCSP is not the revocation source (`RevocationMode = NoCheck` for client validation). Every operation reads current database credential/agent status, expiry, assignment and authorization version. Database failure denies authority. This does not disable the agent's server-certificate validation. |
| Cache boundary | Do not enable `AddCertificateCache`/`ICertificateValidationCache` for agent authentication. Also require uncached resource/operation authorization and atomic version checks at mutation admission, even over an already-open or resumed TLS connection. |

The handshake callback may allow the expected untrusted-self-signed chain condition **only after exact registered pin and independent profile validation**; it cannot ignore arbitrary certificate failures. Kestrel TLS performs private-key-possession proof. A known pending certificate can authenticate only a pending-proof identity. An expired/revoked/unknown installation cannot operate merely because TLS or a cached identity once succeeded. Tests must cover revocation on an existing connection and a same-key/different-DER certificate.

The agent validates the backend's server TLS chain, SAN/hostname, lifetime and server-auth use against explicitly provisioned trust. No accept-all server callback, HTTP fallback or bearer token substitute. Disable TLS early data for state-changing calls. Separate server TLS material, agent keys and the ADR-0006 Data Protection PFX. No backend client-certificate CA/signing key is needed for exact pinning.

Current HTTP-only development Compose/Nginx is not ready for pairing. A separate reviewed bootstrap provisions a distinct development HTTPS server certificate with the SAN actually used by Windows, trusts its public issuer only where needed, and provides trusted HTTPS for both the operator pairing page and agent listener. Prefer localhost when routing is genuinely localhost; otherwise approve the exact reachable development name. Never import an agent client leaf as a general Windows root or overwrite existing root material. Production uses operator-managed server TLS/trust and packaging policy; the development trust procedure is not production certification or an off-host-backup prerequisite for disposable data.

### 3. Installation and pairing without certificate handling by the operator

The generic package contains the service, a small local setup helper, version/integrity information and install/uninstall instructions, **not secrets**. The installer creates protected local identity automatically: a non-exportable machine CNG key and self-signed client certificate. Prefer TPM backing when available; software-backed keys are allowed initially under a trusted-host-administrator assumption. A privileged full clone can copy software identity/state; do not promise clone detection or host-compromise resistance.

An operator never constructs a CSR or copies fingerprints. The following two-sided flow prevents a stolen code alone from substituting an agent certificate:

| Step | User experience and durable effect |
| --- | --- |
| Install | Run the reviewed package with installation privilege. Open its local pairing helper; it shows the backend HTTPS address and an unenrolled identity, with no SQL execution readiness. The Windows service owns the private key. |
| Request grant | In the authenticated HTTPS FlowPlane UI, select the approved ProviderInstance/agent assignment and request pairing. Create grant UUID, intended AgentId, exact requesting issuer/subject, expected agent enrollment/authorization version, assignment/version and database expiry. Display one random 256-bit code once, proposed ten-minute lifetime; persist only its hash. No secret in URL/download/arguments/logs/browser storage. |
| Submit code | Paste the code into the local helper's protected input. It passes it by ACL-restricted local IPC; the service sends the code, idempotent claim UUID and public certificate over server-authenticated HTTPS **without** a TLS client certificate. Validate bounded input and strict certificate profile. Atomically reserve this grant for exactly one claim/certificate, not an active agent. Code reuse with a different claim/key fails. Clear the code from UI/memory as soon as practical; never journal it. |
| Prove possession | After the pending public pin commits and reaches the listener snapshot, reconnect with that certificate over mTLS. A one-use server nonce is bound to grant/claim/certificate and proof request ID; the pending-only proof endpoint verifies mTLS identity and durably consumes the nonce. Identical replay returns its immutable proof receipt, not a new nonce/expiry/authority; conflicting replay fails. No CSR or custom request-signing protocol is needed. A pending identity cannot poll, renew, obtain commands or submit operation receipts. |
| Confirm pairing | Both local helper and operator UI show the same short verification phrase, derived from the server nonce, grant/claim and exact certificate. The operator explicitly confirms the match and intended machine/assignment in the authenticated UI. The phrase is a confirmation aid, not a credential. A different/racing claim never silently replaces it; reject/cancel and request a fresh grant on mismatch. |
| Redeem atomically | In a short transaction, require unexpired pending grant, proof, exact certificate, original authorized operator/resource context, expected agent enrollment/authorization version, unchanged assignment version and confirmation. Mark grant Redeemed, bind certificate to AgentId and activate/increment authorization version exactly once. Only after commit can the service observe Active and report health/readiness. |

Grant states: Issued → Claimed/PendingProof → Proven/AwaitingConfirmation → Redeemed; Expired/Cancelled are non-redeemable. No pending state grants execution authority. Rate-limit code attempts and pending claims. Database uniqueness and locked CAS enforce one live enrollment transition per AgentId and initial provider assignment, one claim per grant, and one current active credential. Issuing a replacement grant explicitly cancels the old pending transition under the same lock; it never replaces an active assignment or unsettled execution. Activation compares captured agent/assignment versions, not merely grant state. Rotation, revocation and enrollment share that fencing/lock protocol; revocation invalidates every pending grant. Bound pending retention/cleanup. A high-entropy code is not a short guessable numeric PIN. The UI/helper clears it; tracing, HAR and credential screenshots remain prohibited.

The service durably stores the non-secret grant/claim/proof request IDs locally before clearing the code. Lost responses replay the **same claim and exact certificate** to recover the committed receipt. Pending-only mTLS proof/status can recover after restart without the code; it neither resets the consumed nonce nor extends expiry. After activation, reconnect with mTLS and the claim ID, never issue another enrollment or native command. A crash before reservation can retry the same in-memory request; loss of the code/request before a committed claim requires a fresh operator grant. A consumed receipt cannot reactivate a revoked installation. Enrollment cannot be transferred to another certificate by possession of the old code. Declined/expired claims require a fresh grant, not silent reassignment.

### 4. Rotation, revocation and installation lifetime

Initial certificate lifetime proposal: 90 days, rotation at day 60, receipt-recovery overlap at most one hour. Credential states are PendingProof → Active → RetiringReceiptsOnly → Retired, with Revoked rejecting all authority. The current active credential requests rotation against its expected credential/agent version; commit and publish the new pending pin, prove the new key over pending-only mTLS, then CAS activation against that still-current version. Atomically make the new pin Active, increment authorization version and make the old pin RetiringReceiptsOnly. The old pin can recover its rotation receipt or upload immutable facts for already-admitted operations only; it cannot poll commands or obtain any native-call admission. After the bounded overlap it is Retired and rejected. Revocation overrides overlap immediately.

For initial B, normal rotation/assignment replacement requires settled execution, checked under the shared admission lock. Existing captured versions cannot silently continue mutations under a replacement credential. Emergency re-enrollment after expiry/loss/revocation preserves unsettled obligations and grants read-only recovery only; configure/start does not resume automatically. Do not require the old private key in Core or authorize arbitrary same-key certificates. No rotation resets operation evidence. Expiry/loss/revocation needs a fresh operator pairing grant and explicit assignment reconfirmation.

Revocation changes durable status/authorization version, blocks new operations and invalidates new admissions independently of TLS connection reuse. It cannot undo a previously admitted SQL call or cancel a running package. Late receipts from a revoked identity are not trusted automatically. Authorized independent exact-ID observation or audited recovery supplies evidence instead.

One fenced active incarnation per installation; ordinary copied installations are quarantined on conflicting sessions. Configuration copies without the key cannot authenticate. Full privileged cloning remains a documented limitation; revoke/re-enroll rather than infer identity from hostname. Uninstall stops/removes the service but does not cancel SQL, release uncertain capacity, delete unresolved journal/key evidence or modify SSISDB. Reinstall must not silently reset identity or reuse a journal against another binding.

### 5. PostgreSQL and local journal protocol

PostgreSQL owns immutable Run/Attempt intent, global active-Run capacity, captured agent/provider/source/revision/authorization versions, operation IDs/ordinals/digests, native-call admissions, once-set native correlation, ownership/fences and audited settlement. Discovery generations are not execution storage. Core remains provider-independent; SSIS codecs/public SQL stay in Providers.Ssis, including the adapter hosted in the agent. No arbitrary SQL, shell, PowerShell, plugins or caller-selected executable commands are accepted.

The initial typed SSIS surface is resolve/preflight, create, set only Basic logging and asynchronous system options, start and read-only observe. The original four fixed mutation markers remain bounded on the Attempt; do not invent a generic remote-job table. Every mutation binds Run/Attempt/operation, AgentId/incarnation, provider/source/principal, profile/revision, captured versions, fence, body digest and expiry. Service-side target allowlisting and Core policy both apply. Existing parameter-free/64-bit/non-Scale-Out/null-reference rules and visible-active-execution preflight remain unchanged.

| Durable stage | Guarantee |
| --- | --- |
| IntentCommitted / Offered | Commit intent/capacity before HTTP 202/delivery. Delivery is not SQL permission. |
| AgentAccepted | Flush operation ID/digest/context to the ACL-protected local journal; acknowledge idempotently. |
| NativeCallAdmitted | Core atomically checks versions/fence/order/expiry and commits a one-shot permit for this live incarnation. A lost permit response yields reconciliation, not another positive permit. |
| MayHaveInvoked | Agent flushes the marker **before** issuing SQL once. Crash between marker and invocation is conservatively uncertain. |
| NativeResultKnown | Flush returned native ID/result locally, then replay only its immutable receipt until Core commits it. |
| CoreResultCommitted | Seal provider-qualified native ID/creation facts in PostgreSQL before authorizing configuration/start. Each subsequent mutation has its own admission/receipt. |
| Settled / ActionRequired | Verified evidence advances or settles. Unknown admitted mutation retains capacity; no automatic create/configure/start retry. |

Local journal: bounded framed/versioned records with integrity/torn-write detection and durable flush/atomic replacement as appropriate. Store operation/context digests, markers, known native ID/creation facts and Core receipt acknowledgement—not code/token/password/parameter values or raw diagnostics. Journal/write/flush failure prevents a new call. Disk-full, corruption, missing expected evidence or reinstall cannot turn admitted work into an uninvoked operation. Compact only Core-acknowledged settled evidence; never evict unresolved records to satisfy a quota. Journal format/fault tests are foundation work; Run/Attempt admissions are B-06/B-08 integration.

Core/agent restart reconciles committed IDs and receipts before readiness. Read-only exact-ID queries may retry; unknown create cannot be adopted by package/path/time similarity. Automatic takeover for no-native-admission work must atomically verify that fact and fence the old incarnation. Known-ID observation recovery grants no mutation authority. SQL cannot enforce FlowPlane's fence; lease expiry/revocation cannot stop an old already-admitted call. No exactly-once or cross-database transaction claim. Native status 9 is not automatically success.

### 6. Audited ActionRequired operational recovery

No general recovery UI, force-unlock endpoint or timer-based release is authorized. Use a separately reviewed operator runbook and narrow application recovery command only when implemented and approved:

1. Authenticate the exact operator, capture Run/Attempt/operation and source identity, preserve Core/journal evidence and safe reason codes. Freeze new authority; do not delete/reinstall to hide state.
2. Establish quiescence of every old call-issuing process/connection; fencing or killing a lease alone does not prove a delayed SQL call cannot still complete. Investigate outstanding SQL effects without broadening privileges or executing packages.
3. With a durable native ID, verify exact source/creation facts and authoritative terminal/settlement evidence. Created, invisible, missing or retention-removed rows do not prove settlement. Preserve status 9/unclassified facts as ActionRequired unless sufficient provider evidence exists.
4. Without a durable ID, require affirmative operation-specific no-creation evidence. Empty catalog/time-window searches, timeouts and heuristic matching are insufficient. If evidence is unavailable, keep the slot and ActionRequired indefinitely; any exceptional risk-accepting intervention requires separate approval and is not described as safe duplicate prevention.
5. Under current versions and a short fenced PostgreSQL transaction, compare expected reconciliation state and commit only proven settlement/no-native closure, slot release and immutable audit. Record operator, evidence references, before/after fences, reason and timestamp without secrets. Reconcile a lost commit acknowledgement by durable recovery/operation ID, never repeat native work.

### 7. Basic health and bounded extensions

AgentHealth reports authenticated last contact/heartbeat, version/protocol, enrollment state, readiness and relevant capability Available/Unavailable/Unknown with freshness/safe reasons. Connected is not SQL-ready. Foundation health may truthfully show execution Unknown until B-02/B-07 provide proof.

Agent host, agent process and SQL Server host remain distinct. HostObservations and DataFlowTelemetry are optional typed PoCs with mandatory feasibility/limitations reports. No generic host entity, metrics/history pipeline, dashboard, alerting or SSDT-debugger parity. Advanced statistics require separately approved representative fixtures/logging/execution; this ADR authorizes none.

## Alternatives considered

- Persistent connection: unnecessary reconnect/session complexity for bounded commands; polling is sufficient initially.
- Bearer-only or custom application PoP: bearer replay risk, or additional signed-request/nonce protocol; use standard TLS possession proof plus durable operation deduplication.
- Per-agent certificates issued by a new backend CA: adds a signing key/lifecycle without benefit for the initial exact public-pin registry; no CA service is introduced.
- Nginx certificate-header authentication: expands trusted-proxy and direct-access boundaries; initial direct Kestrel termination avoids it. Any later termination/passthrough change needs review.
- Manual CSR/fingerprint enrollment: technically possible but avoidable operator friction; the setup helper and two-sided confirmation automate identity handling.
- LocalSystem, interactive-account execution, password mirroring or broad SQL roles: inappropriate privilege or wrong identity proof.
- PostgreSQL alone or local journal alone: PostgreSQL cannot recover an unreported returned ID after agent crash without local evidence; a local journal cannot be the shared orchestration authority. Neither eliminates ambiguous native effects.

## Consequences and implementation gates

The bounded [Windows Agent foundation #28](https://github.com/aaliakbarian/flowplane/issues/28) is a child of Milestone B parent #16, separate from B-07's provider-owned SSIS adapter. Foundation covers service/package/setup, pairing/mTLS/revocation/rotation, minimal journal primitives and AgentHealth using synthetic operations only. Both foundation and B-02 depend on completed B-01; foundation does not block B-02's independent interactive proof. B-02's actual service-token subproof requires foundation readiness, and B-02 remains incomplete until its required evidence is verified; it still gates execution-specific implementation. B-06/B-08 integrate durable Run commands; B-10 completes operator UI and B-11 supplies independent security/live acceptance. Preserve all other relationships, including foundation as a prerequisite of B-07/B-08/B-10; no new issue or broad dependency rewrite.

New agent/enrollment/assignment/authorization persistence is required, but exact tables, EF mappings and generated Up/Down/SQL need a separate schema gate; no migration is generated/applied here and no automatic startup migration is allowed. Separate local TLS/SCM/SQL grants, packaging, native proof and real acceptance approvals remain mandatory. A new supported .NET certificate-auth package may be required during implementation; this record adds no dependency.

RED/GREEN and independent review must cover token replay, concurrent claims/confirmation/rotation, substitution/mismatched phrase, pending-certificate isolation, revoked credentials over existing connections, no-EKU/self-signed-unknown/expired certificates, spoofed Nginx headers, listener isolation, malicious command/endpoint, exact-context/fence races, journal/disk faults, every native-call crash boundary and lost acknowledgements. Real PostgreSQL proves atomicity after migration approval; real TLS proves listener behavior; intended service-token native tests prove feasibility only after external-operation approval. A static API review is not a passing runtime TLS or SQL test. Independent security acceptance remains mandatory before Milestone B closure.
